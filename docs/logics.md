# Документация по логике паттернов файла closed_ov_ah.py

## 1. Что делает этот файл

Файл [closed_ov_ah.py](../closed_ov_ah.py) отвечает за поиск и определение паттернов старых стратегий в истории изменений матчей. Он анализирует данные, которые приходят из обработчика матчей, и пытается выявить ситуации, где коэффициент или линия были близки к закрытию, а затем отправляет Telegram-уведомление при совпадении определённого сценария.

Основная задача файла — не собирать данные и не работать с браузером, а проверять историю матчей на наличие повторяющихся паттернов, которые могут указывать на сильную сигнализацию.

---

## 2. Какой общий сценарий работы логики

Логика в [closed_ov_ah.py](../closed_ov_ah.py) работает следующим образом:

1. Принимает `match_history` — историю матчей и изменений по ним.
2. Преобразует данные в список `entries`.
3. Проверяет, нет ли сценария для `over`-параметра.
4. Проверяет, нет ли сценария для `AH` (азиатская фора).
5. Если найден паттерн, отправляет сообщение через Telegram.
6. Возвращает список `match_id`, которые подошли под условие.

То есть файл работает как “детектор сигнала” по истории событий матча.

## 3. Константы и их назначение

В начале файла задаются два важных параметра:

```python
THRESHOLD = 0.61
START_ODD = 0.90
```

### `THRESHOLD`

Это верхний порог для последнего коэффициента перед закрытием линии. В текущей логике значение должно быть меньше или равно `0.61`:

- `0.60` подходит;
- `0.61` подходит;
- `0.62` не подходит.

### `START_ODD`

Несмотря на название, в текущей логике это минимальный подтверждающий коэффициент. Среди более ранних записей ищется значение больше или равно `0.90`:

- `0.89` не подходит;
- `0.90` подходит;
- `0.95` подходит.

Иначе говоря, для срабатывания over-паттерна нужны два условия:

1. Последний коэффициент перед `Closed` должен быть `<= THRESHOLD`.
2. В одной из предыдущих записей с той же линией должен быть коэффициент `>= START_ODD`.

Поиск выполняется назад по сохранённой истории: от записи перед `Closed` к более старым записям. Это не поиск «вверх по текущей таблице», а проверка последовательности изменений, сохранённой в `entries`.

Пример подходящей истории:

```text
0.92 -> 0.91 -> 0.88 -> 0.60 -> Closed
```

Здесь `0.60` проходит проверку `THRESHOLD`, а `0.92` проходит проверку `START_ODD`. Если линия тотала между этими записями не менялась, отправляется уведомление.

Важно: пороги сравниваются с исходными значениями коэффициентов. При отправке в Telegram коэффициент отдельно преобразуется для отображения, но это не влияет на поиск паттерна.

### Новая стратегия: снижение тотала (`drop_ov_ah.py`)

Стратегия реализована отдельно в [drop_ov_ah.py](../drop_ov_ah.py) и вызывается общим Over-координатором из [closed_ov_ah.py](../closed_ov_ah.py).

`_find_over_total_drop_pattern` сравнивает последнюю валидную линию с предыдущими валидными линиями того же счёта, двигаясь назад по истории. Если с ближайшей линией нужного увеличения нет, проверяются более ранние линии; поиск прекращается на смене счёта. Строки `Closed`, строки без числового тотала или коэффициентов Over/Under, строки со значением из `SKIPMATCH` и строки вне окна `DROP_WINDOW_MINUTES` пропускаются. Сигнал отправляется при первом найденном увеличении от `MIN_DROP_THRESHOLD` включительно до `MAX_DROP_THRESHOLD` не включительно.

После изменения счёта стратегия ждёт закрытия Over-линии и подтверждения новой линии. Если первая заполненная линия после `Closed` имеет тот же тотал, что и последняя заполненная линия до закрытия, она считается устаревшей: её счёт нормализуется к старому, а ожидание продолжается через последующие `Closed`. Первая заполненная линия с отличающимся тоталом подтверждает переход и получает новый счёт, но сама не сравнивается с тоталом старого счёта и не может вызвать сигнал. Если `Closed` и подтверждение новой линии не появились в течение 3 минут от первой записи с новым счётом, первая следующая валидная открытая строка принимается без нормализации счёта. Последующие сравнения идут между строками нового счёта.

После смены счёта первый отличающийся тотал лишь подтверждает новую линию; для сигнала нужна следующая валидная линия того же счёта с требуемым ростом.

Пара записей, на которой найдено подходящее изменение тотала, не анализируется, если поле `time` или `match_time` хотя бы одной записи содержит значение из `SKIPMATCH` в [config.py](../config.py). По умолчанию исключены `FT` и `ET`, включая дополнительное время вида `ET+7`.

Если парсер запущен посреди матча и закрытие рынка не попало в историю, самая ранняя сохранённая линия с текущим счётом используется как доступная база. Это может быть не фактическая исходная линия рынка. Если в текущем непрерывном отрезке есть только одна числовая линия, сравнивать её не с чем и сигнал не отправляется.

При `DEBUGMODE = 1` исходная история для стратегий Closed Over/AH сохраняется в `data_closed_ov_ah.json`, а подготовленная для стратегии снижения тотала история — в `data_drop_ov_ah.json`. Во второй истории счёт в записях временно нормализован; исходная история при этом не изменяется.

Уведомления новых стратегий отправляются в `NEW_STRATEGY_CHANNEL_ID` из `.env`; классические Over- и AH-уведомления продолжают использовать `CHANNEL_ID`. Дедупликация и последующее редактирование уведомлений учитывают канал назначения.

## 5. Вспомогательные функции и их назначение

### 5.1. `_to_float(value)`

```python
def _to_float(value):
```

Назначение:

- перевести значение в число `float`;
- если значение не может быть преобразовано, вернуть `None`.

Зачем нужно:

- коэффициенты могут приходить как строки, например `'1.55'`;
- чтобы сравнивать их с порогами, их надо приводить к числу.

---

### 5.2. `_normalize_ah_text(value)`

```python
def _normalize_ah_text(value):
```

Назначение:

- привести значение форы к нормальному строковому виду;
- убрать лишние пробелы;
- вернуть `None`, если значение пустое.

Зачем нужно:

- AH-значения могут приходить в разных форматах, например `-0.5`, `0/-0.5`, `0`, `+0`. Четвертные форы `0/0.5` и `0/-0.5` нормализуются как величина `0.25` со стороной первой и второй команды соответственно; они не считаются нулевой форой.
- нормализация помогает унифицировать проверки.

---

### 5.3. `_is_exact_zero_ah(value)`

```python
def _is_exact_zero_ah(value):
```

Назначение:

- определить, является ли значение AH нулём (`0`, `+0`, `-0` и т.п.).

Это нужно, потому что нулевая фора имеет особую семантику и не должна обрабатываться.

---

### 5.4. `_is_away_zero_split_handicap(value)`

```python
def _is_away_zero_split_handicap(value):
```

Назначение:

- определить, является ли значение форматом вида `0/-0.5` или аналогичным вариантом, которым обозначается фора второй команды.

Пример:

- `0/-0.5`

Это важно, потому что у такой форы направление и логика расчёта отличаются от обычной форы.

---

### 5.5. `_ah_sign(value)`

```python
def _ah_sign(value):
```

Назначение:

- понять знак форы: отрицательная, положительная или нулевая.

Что возвращает:

- `-1` — отрицательная фора;
- `1` — положительная фора;
- `0` — нулевая фора;
- `None` — если значение пустое/неверное.

Это нужно, чтобы понять, у какой команды была фора и в каком направлении смотреть коэффициенты.

## 6. Основные функции паттернов

### 6.1. `_collect_match_entries(data)`

```python
def _collect_match_entries(data):
```

Назначение:

- взять `initial` и все элементы из `changes`;
- собрать их в единый список `entries` для дальнейшего анализа.

Зачем нужно:

- паттерн проверяется по последовательности событий, а не по одному полю;
- чтобы анализировать историю изменения коэффициентов и линий, нужно объединить все записи.

---

### 6.2. `_get_last_entry_before_closed(entries, field_name)`

```python
def _get_last_entry_before_closed(entries, field_name):
```

Назначение:

- найти последнюю запись до состояния `Closed` у нужного поля: `ov` или `ah`;
- вернуть сам объект записи и его индекс.

Зачем нужно:

- именно перед закрытием линии чаще всего формируется тот сигнал, который мы ищем;
- тут определяется “база” для последующей проверки паттерна.

---

### 6.3. `_find_over_pattern(entries, match_id)`

```python
def _find_over_pattern(entries, match_id):
```

Назначение:

- проверить историю матча на паттерн для total over;
- определить, есть ли ситуация, когда линия была закрыта после низкого коэффициента и перед этим была более высокая линия.

Что делает функция:

- смотрит, был ли последний элемент для `ov` в состоянии `Closed`;
- берёт последнюю запись до закрытия;
- проверяет, что коэффициент в последней записи перед `Closed` не превышает `THRESHOLD`;
- идёт назад по истории, к более ранним записям, и ищет коэффициент не ниже `START_ODD` при одинаковой линии тотала;
- если паттерн найден, вызывает отправку уведомления.

Возвращает:

- `True`, если паттерн найден;
- `False`, если нет.

---

### 6.4. `_send_over_notification(match_id, last_entry, last_total, last_over_odds)`

```python
def _send_over_notification(match_id, last_entry, last_total, last_over_odds):
```

Назначение:

- отправить Telegram-сообщение для найденного over-паттерна.

Что в него передаётся:

- `match_id`;
- данные матча из последней подходящей записи;
- итоговый тотал;
- коэффициент.

Зачем нужно:

- логика должна быть разделена на “поиск паттерна” и “отправка уведомления”; так проще тестировать и отлаживать.

---

### 6.5. `_find_ah_pattern(entries, match_id)`

```python
def _find_ah_pattern(entries, match_id):
```

Назначение:

- проверить историю матча на паттерн для азиатской форы (AH).

Что делает функция:

- находит последнюю запись до `Closed` для поля `ah`;
- анализирует знак форы (`+`, `-`, `0`);
- определяет, какая сторона форы рассматривалась (`home` или `away`);
- проверяет, что коэффициент на этой форе был низким;
- ищет более раннюю строчку с таким же AH и высоким коэффициентом;
- если найдено совпадение, вызывает отправку уведомления.

Возвращает:

- `True`, если паттерн найден;
- `False`, если нет.

### 6.6. `_send_ah_notification(match_id, last_entry, last_ah, last_ah_odds, odds_side)`

```python
def _send_ah_notification(match_id, last_entry, last_ah, last_ah_odds, odds_side):
```

Назначение:

- отправить Telegram-уведомление для паттерна AH.

Что делает:

- формирует корректную строку форы;
- если это не нулевая фора и формат без `-`, добавляет знак `-` там, где нужно;
- передаёт все данные в `send_telegram_notification`.

Зачем нужно:

- для AH-вариантов используется отдельный формат отправки, отличный от over-сценария.

## 7. Главная функция `find_pattern_matches`

```python
def find_pattern_matches(match_history, on_notification_sent=None):
```

Это главная функция этого файла.

Что она делает:

1. Проходит по всем матчам из `match_history`.
2. Для каждого матча собирает историю `entries`.
3. Проверяет `over`-паттерн.
4. Проверяет `AH`-паттерн.
5. При успешной отправке вызывает необязательный callback с ID матча, типом рынка, ID Telegram-сообщения и исходным текстом.
6. Если хотя бы один паттерн найден, добавляет `match_id` в список.
7. Возвращает список совпавших матчей.

Это функция-оркестратор: она не сама вычисляет паттерны, а вызывает более мелкие функции, которые выполняют конкретные шаги.

Возвращаемое значение:

- список `match_id`, по которым были найдены подходящие сигналы.

## 8. Что происходит в блоке `if __name__ == "__main__":`

В конце файла есть блок:

```python
if __name__ == "__main__":
```

Он нужен для ручной проверки логики.

Что происходит:

- выполняется попытка открыть файл `matches_realtime.json`;
- если файл есть, данные загружаются в `match_history`;
- вызывается `find_pattern_matches(match_history)`;
- результат выводится в лог.

Это удобно для локального тестирования без запуска всего проекта, но в рабочем приложении эта логика обычно не используется.

## 9. Обязательные условия для корректной работы

### 9.1. Корректная структура `match_history`

Функции ожидают, что данные будут иметь структуру вроде:

- `match_id` → словарь с `initial` и `changes`;
- внутри записей есть поля вроде `ov`, `ah`, `team1`, `team2`, `score`, `league`.

Если структура изменится, паттерны могут перестать срабатывать.

### 9.2. Правильный формат odds

Поскольку используется `_to_float`, важно, чтобы коэффициенты были либо числами, либо строками, которые можно перевести в число.

### 9.3. Параметры `THRESHOLD` и `START_ODD`

Эти константы напрямую влияют на результат поиска:

- увеличение `THRESHOLD` делает условие для последнего коэффициента мягче и может дать больше сигналов;
- уменьшение `THRESHOLD` делает условие строже и может дать меньше сигналов;
- увеличение `START_ODD` требует более высокого раннего коэффициента и делает подтверждение строже;
- уменьшение `START_ODD` позволяет использовать более низкий ранний коэффициент и делает подтверждение мягче.

В текущей конфигурации используются:

```python
THRESHOLD = 0.61
START_ODD = 0.80
```

Это означает: сначала ожидается падение коэффициента до `0.61` или ниже, затем в более ранней истории должна найтись отметка `0.90` или выше, после чего линия закрывается.

### 9.4. Telegram-уведомления

Так как в функции используется `send_telegram_notification`, должны быть корректно настроены:

- Telegram-соединение;
- параметры бота;
- каналы/чаты для отправки;
- нужный формат данных.

---

## 10. Краткое резюме

Файл [closed_ov_ah.py](../closed_ov_ah.py) выполняет роль координатора legacy Over/AH-стратегий и анализа матчей. Он:

- читает историю изменений по матчам;
- ищет сигнальные паттерны для `over` и `AH`;
- проверяет соблюдение условий по коэффициентам;
- при совпадении отправляет Telegram-уведомление;
- возвращает список матчей, которые подошли под условия.

То есть это файл, который отвечает не за запуск проекта, а за “смысловую” часть — поиск выгодных сигналов по истории событий.
