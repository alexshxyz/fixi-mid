# Документация по файлу storage.py

## 1. Назначение файла

Файл [storage.py](../storage.py) отвечает за постоянное хранение обработанных матчей и расчёт статистики по ним.

В текущей реализации данные хранятся в JSON-файле, а не в базе данных. Модуль предоставляет общий интерфейс для записи, чтения, проверки дубликатов и группировки матчей.

Основные задачи файла:

- создать файл хранилища при первом запуске;
- загрузить список сохранённых матчей;
- проверить, не сохранялся ли уже такой прогноз;
- добавить новый матч в `matches.json`;
- получить матчи за период;
- посчитать победы, поражения и возвраты;
- сгруппировать статистику по лигам.

`storage.py` не открывает браузер, не анализирует коэффициенты и не отправляет Telegram-сообщения. Он предоставляет функции хранения, которыми пользуются остальные модули.

---

## 2. Место storage.py в работе скрипта

Общий поток данных выглядит так:

```text
main.py
  |
  | вызывает init_storage() при запуске
  v
storage.py <---------------- telegram_notifier.py
  |                                  |
  | хранит matches.json              | проверяет дубликат
  |                                  | и сохраняет найденный прогноз
  v                                  v
stats.py и tools/stats_manual.py
  |
  | читают матчи и считают статистику
```

Связь с логикой паттернов строится косвенно:

```text
parser.py -> logics.py -> telegram_notifier.py -> storage.py
```

То есть `logics.py` находит подходящий паттерн и вызывает уведомитель, а `telegram_notifier.py` перед отправкой сообщения проверяет дубликат и сохраняет матч через `storage.py`.

---

## 3. Как используется storage.py при запуске

В [main.py](../main.py) модуль импортируется так:

```python
from storage import init_storage
```

В начале `main()` вызывается:

```python
init_storage()
```

После этого создаётся `matches.json`, если файла ещё нет. Затем запускается браузер и основной мониторинг матчей.

Сам `parser.py` не использует `storage.py` для истории live-коэффициентов. Его временная история хранится в глобальном `match_history`, а для восстановления после перезапуска используется отдельный файл `match_state.json`.

---

## 4. Импорты и настройки

В файле используются:

- `json` — чтение и запись JSON;
- `os` — чтение переменной окружения и построение пути;
- `setup_logger` из [logging_config.py](../logging_config.py) — получение настроенного логгера;
- `date` из `datetime` — установка текущей даты для нового матча;
- `Path` из `pathlib` — безопасная работа с путями и каталогами.

### `APP_DIR`

```python
APP_DIR = Path(__file__).resolve().parent
```

Содержит абсолютный путь к каталогу проекта.

### `MATCHES_FILE`

```python
MATCHES_FILE = os.environ.get(
    'MATCHES_FILE',
    str(APP_DIR / 'matches.json')
)
```

Определяет путь к JSON-хранилищу.

Если переменная окружения `MATCHES_FILE` задана, используется её значение. Иначе файл создаётся рядом с `storage.py` под именем `matches.json`.

Это позволяет вынести хранилище в другой каталог без изменения исходного кода.

## 5. Внутренние функции работы с JSON

### 5.1. `_ensure_matches_file()`

Проверяет, что каталог и файл хранилища существуют.

Алгоритм:

1. преобразует `MATCHES_FILE` в объект `Path`;
2. создаёт родительский каталог, если его нет;
3. создаёт файл с содержимым `[]`, если файла нет;
4. возвращает путь к файлу.

Эта функция вызывается перед чтением и записью, поэтому остальные функции могут рассчитывать, что каталог хранилища уже подготовлен.

### 5.2. `_load_matches()`

Загружает список матчей из JSON-файла.

Если файл содержит корректный JSON-массив, массив возвращается без изменений.

Если файл:

- отсутствует;
- пустой или повреждённый;
- содержит не список;
- недоступен для чтения,

функция записывает в него пустой список `[]` и возвращает пустой результат.

Это позволяет приложению восстановить рабочее состояние после повреждения файла, но старые повреждённые данные при этом теряются.

### 5.3. `_save_matches(matches)`

Записывает переданный список матчей в `MATCHES_FILE`.

Перед записью снова вызывается `_ensure_matches_file()`. JSON форматируется с отступами, а в конце добавляется перевод строки.

## 6. Переход с базы данных на JSON

Ранее модуль содержал совместимый с PostgreSQL интерфейс `_get_connection()` и константу `TABLE_NAME`. В текущем проекте они больше не используются: все записи и статистика работают через `matches.json`.

Поиск вызовов по проекту подтверждает, что `_get_connection()` не импортируется и не вызывается. Поэтому функция удалена как мёртвый код. Для работы текущих модулей это не требует дополнительных изменений.

Если внешний код за пределами этого проекта импортировал `_get_connection()` или `TABLE_NAME`, такой код нужно отдельно перевести на функции JSON-хранилища.

## 7. Инициализация и защита от дубликатов

### 7.1. `init_storage()`

```python
def init_storage():
```

Создаёт файл `matches.json`, если его ещё нет, и возвращает `True`.

Функция используется в `main.py` перед запуском браузера и мониторинга.

Она не очищает существующие данные и не проверяет их содержимое. Её задача — только подготовить файл и каталог.

### 7.2. `check_duplicate_match(link, prediction)`

```python
def check_duplicate_match(link, prediction):
```

Проверяет, есть ли в хранилище матч с такой же парой:

- `link`;
- `prediction`.

Если хотя бы один из аргументов пустой, возвращается `False`.

Затем функция загружает все записи и сравнивает поля `link` и `prediction`. Возвращает:

- `True`, если совпадение найдено;
- `False`, если совпадения нет.

Функция используется в [telegram_notifier.py](../telegram_notifier.py) перед отправкой и сохранением найденного прогноза.

Одинаковая ссылка с другим прогнозом считается другой записью. Дубликатом является только полное совпадение обоих полей.

## 8. Сохранение матча

### `save_match(...)`

```python
def save_match(
    league,
    home_team,
    away_team,
    prediction,
    odds,
    link,
    final_score=None,
    result=None,
    script=None,
    date_value=None,
):
```

Добавляет прогноз в JSON-хранилище.

### Обработка аргументов

#### `odds`

Если значение передано, функция пытается преобразовать его в `float`. Если преобразование не удалось, в запись попадает `None`.

#### `date_value`

Если дата не передана, используется текущая дата в формате ISO:

```text
YYYY-MM-DD
```

### Формат записи

В `matches.json` сохраняется объект:

```python
{
    "league": "Example League",
    "home_team": "Team A",
    "away_team": "Team B",
    "prediction": "Over 2.5",
    "odds": 0.8,
    "final_score": null,
    "result": null,
    "link": "https://example.com/match/123",
    "script": "script_name",
    "date": "2026-09-02",
    "source": "Crown"
}
```

Поле `source` всегда получает значение `Crown`, потому что прогнозы собираются из этого источника коэффициентов.

### Порядок действий

1. Нормализуется значение odds.
2. Определяется дата.
3. Создаётся словарь записи.
4. Загружается текущий список матчей.
5. Проверяется дубликат через `check_duplicate_match()`.
6. Если дубликат найден, запись не добавляется и возвращается `(None, None)`.
7. Если дубликата нет, запись добавляется и сохраняется в файл.
8. Возвращается пара `(row_order, row_order)`, где `row_order` — порядковый номер записи в списке.

### Связь с telegram_notifier.py

В [telegram_notifier.py](../telegram_notifier.py) после проверки ссылки и прогноза вызывается `save_match()`. Поэтому именно этот модуль является точкой фактического сохранения найденных сигналов.

## 9. Функции чтения и статистики

### 9.1. `get_all_matches()`

Возвращает все записи из `matches.json`.

Функция используется в [tools/stats_manual.py](../tools/stats_manual.py) для ручного просмотра и анализа всей истории.

### 9.2. `get_matches_in_date_range(start_date, end_date)`

Возвращает матчи за заданный период.

Границы интервала работают так:

- `start_date` включается;
- `end_date` не включается.

Условие фильтрации:

```python
start_date <= match_date < end_date
```

Так как дата хранится строкой в формате `YYYY-MM-DD`, лексикографическое сравнение работает корректно при условии, что все даты используют один формат.

Функция используется в [stats.py](../stats.py) для расчёта статистики за текущий период и в `tools/stats_manual.py` для ручных отчётов.

### 9.3. `calculate_stats(matches)`

Считает общие результаты для переданного списка матчей.

Возвращает кортеж:

```python
(total, wins, losses, voids)
```

Подсчёт выполняется по значению поля `result`:

- `Won` — победа;
- `Lost` — поражение;
- `Void` — возврат/аннулированный результат.

Другие значения, включая `None`, не увеличивают отдельные счётчики, но входят в `total`.

### 9.4. `get_stats_by_league(matches)`

Группирует статистику по полю `league`.

Если поле отсутствует, используется группа `Unknown`.

Результат имеет вид:

```python
{
    "Example League": {
        "total": 10,
        "wins": 5,
        "losses": 3,
        "voids": 2
    }
}
```

Функция не читает файл самостоятельно. Она принимает уже загруженный список матчей, поэтому может использоваться как для полного набора данных, так и для заранее отфильтрованного периода.

## 10. Связь с stats.py и tools/stats_manual.py

### `stats.py`

Сервис статистики импортирует:

```python
from storage import get_matches_in_date_range, calculate_stats
```

Он получает матчи за нужный период и рассчитывает количество:

- всех матчей;
- побед;
- поражений;
- возвратов.

Сервис запускается из `main.py` в отдельном фоновом потоке.

### `tools/stats_manual.py`

Ручной инструмент использует все публичные функции чтения и статистики:

- `get_all_matches()`;
- `get_matches_in_date_range()`;
- `calculate_stats()`;
- `get_stats_by_league()`.

Он позволяет строить отчёты по всей истории, отдельным датам и лигам без запуска браузерного мониторинга.

## 11. Что важно учитывать

### JSON-файл не является базой данных

Все записи загружаются целиком в память, затем весь список записывается обратно в файл. При небольшом объёме данных это просто и достаточно, но для очень большого файла производительность будет снижаться.

### Нет блокировки при параллельной записи

Если несколько потоков или процессов одновременно вызывают `save_match()`, возможны гонки при чтении и записи. В текущем проекте сохранение обычно выполняется из одного основного потока уведомлений.

### Повреждённый файл сбрасывается

При ошибке чтения `_load_matches()` заменяет содержимое на пустой список. Поэтому резервное копирование `matches.json` важно, если история матчей представляет ценность.

### Даты должны иметь единый формат

Для корректной фильтрации даты должны храниться в формате `YYYY-MM-DD`. Передача произвольных строк может привести к неправильному результату сравнения.

### `match_state.json` относится к другому уровню

`matches.json` содержит сохранённые прогнозы и результаты, а `match_state.json` содержит временное состояние live-мониторинга из `parser.py`. Эти файлы нельзя считать взаимозаменяемыми.

---

## 12. Краткое резюме

`storage.py` — это слой постоянного хранения результатов работы скрипта:

- `main.py` подготавливает файл через `init_storage()`;
- `telegram_notifier.py` проверяет дубликаты и сохраняет найденные прогнозы;
- `stats.py` и `tools/stats_manual.py` читают данные и считают статистику;
- `parser.py` использует отдельное состояние мониторинга и напрямую не записывает прогнозы в `matches.json`.

Таким образом, файл отделяет хранение данных от браузерного мониторинга, анализа паттернов и отправки уведомлений.
