# Документация по файлу parser.py

## 1. Назначение файла

Файл [parser.py](../parser.py) является центральным модулем сбора и мониторинга данных о live-матчах.

Он получает уже открытую страницу браузера из [main.py](../main.py), извлекает из HTML данные матчей через Playwright, сохраняет историю изменений коэффициентов и передаёт эту историю в [logics.py](../logics.py) для поиска паттернов.

`parser.py` не отвечает за запуск браузера, настройку сайта или отправку Telegram-сообщений. Его зона ответственности:

- подготовить состояние мониторинга;
- получить список и текущие данные матчей;
- регулярно проверять изменения коэффициентов;
- переживать временную недоступность таблицы;
- периодически перезагружать страницу;
- сохранять состояние перед принудительным перезапуском;
- запускать проверку паттернов после изменения данных.

---

## 2. Место parser.py в работе скрипта

Общий поток работы выглядит так:

```text
main.py
  |
  | открывает Chromium и настраивает страницу
  | выбирает Live, Crown и параметры odds
  v
parser.py
  |
  | получает список матчей
  | извлекает данные и следит за изменениями
  | хранит match_history
  v
logics.py
  |
  | анализирует историю over/AH
  | отправляет Telegram-уведомления
```

### Последовательность запуска

1. `main.py` вызывает `init_storage()` и запускает сервис статистики.
2. `main.py` создаёт браузер и страницу через Playwright.
3. Страница переводится в режим Live, выбирается источник Crown и настраиваются отображаемые коэффициенты.
4. `main.py` загружает сохранённое состояние через `load_state_from_json()`.
5. Если состояния нет, `main.py` собирает ID матчей функцией `collect_matches(page)`.
6. В обоих случаях вызывается одна публичная функция:

   ```python
   parse_and_monitor_match(page, match_ids=None, saved_state=None)
   ```

7. `parser.py` создаёт объект `MatchMonitor` и запускает его методом `run()`.
8. Мониторинг продолжается, пока не потребуется перезапуск браузера или не произойдёт необработанная ошибка.

## 3. Импорты и общие настройки

В начале файла используются стандартные модули:

- `json` — чтение и запись JSON-состояния;
- `os` — проверка существования файла состояния и формирование пути к лог-файлу;
- `time` — задержки, таймер мониторинга и планирование перезапуска;
- `random` — случайный интервал периодической перезагрузки;
- `setup_logger` из [logging_config.py](../logging_config.py) — получение настроенного логгера для диагностических сообщений.

### Общие константы

```python
STATE_SAVE_FILE = "match_state.json"
RESTART_HOURS = 8
```

### `MatchMonitor.match_history`

История матчей хранится как атрибут конкретного экземпляра `MatchMonitor`:

```python
self.match_history = {}
```

Она передаётся в `logics.find_pattern_matches(self.match_history)` для анализа. Благодаря этому два экземпляра `MatchMonitor` в одном процессе не используют общий словарь и не смешивают истории.

Пример структуры:

```python
{
    "12345": {
        "initial": {
            "time": "12:34",
            "ah": {
                "home_ah_odds": "0.75",
                "ah": "-0.5",
                "away_ah_odds": "0.95"
            },
            "ov": {
                "over_odds": "0.80",
                "over": "2.5",
                "under_odds": "1.00"
            },
            "team1": "Team A",
            "team2": "Team B",
            "score": "1-0",
            "league": "Example League"
        },
        "changes": []
    }
}
```

#### `STATE_SAVE_FILE`

Имя JSON-файла, в который сохраняются:

- `match_history`;
- последние данные по каждому матчу (`last_data`);
- список активных ID матчей (`active_match_ids`).

#### `RESTART_HOURS`

Через это количество часов мониторинг сохраняет состояние и выбрасывает `PageRestartRequired`. [main.py](../main.py) перехватывает это исключение, закрывает браузер и перезапускает процесс.

## 4. Исключения

### `PageRestartRequired`

Сигнал для внешнего кода о том, что текущий браузер или страница должны быть перезапущены.

Исключение возникает в двух основных случаях:

- плановый перезапуск через `RESTART_HOURS` часов;
- слишком много неудачных попыток перезагрузить страницу из-за падения страницы или таймаутов.

В `MatchMonitor.run()` это исключение не поглощается, поэтому оно доходит до `main.py`.

### `TableNotReadyError`

Внутренний сигнал, означающий, что таблица `table#table_live` ещё не готова. Он используется функцией `_extract_all_match_data()` и обрабатывается методами `MatchMonitor`.

## 5. Функции работы с состоянием

### 5.1. `MatchMonitor._save_state_to_json(active_match_ids, last_data, path=STATE_SAVE_FILE)`

Сохраняет текущее состояние мониторинга в JSON-файл.

В файл записывается объект:

```python
{
    "match_history": self.match_history,
    "last_data": last_data,
    "active_match_ids": active_match_ids
}
```

Возвращает:

- `True`, если запись прошла успешно;
- `False`, если возникла ошибка.

Функция вызывается перед принудительной перезагрузкой после повторяющихся ошибок и перед плановым перезапуском.

### 5.2. `load_state_from_json(path=STATE_SAVE_FILE)`

Загружает сохранённое состояние из JSON-файла.

Если файл найден и прочитан успешно:

1. JSON преобразуется в словарь;
2. файл удаляется;
3. словарь возвращается вызывающему коду.

Если файла нет или чтение завершилось ошибкой, возвращается `None`.

В [main.py](../main.py) результат используется так:

```python
saved_state = load_state_from_json()

if saved_state:
    parse_and_monitor_match(page, saved_state=saved_state)
```

Удаление файла после чтения предотвращает повторное использование устаревшего состояния при следующем запуске.

## 6. Функции работы со страницей

### 6.1. `_reload_page_with_retries(page, active_match_ids, last_data, ...)`

Перезагружает страницу и ждёт появления таблицы `table#table_live`.
После перезагрузки таблица ожидается до 20 секунд. Если за это время она не стала видимой, попытка считается неудачной.

При ошибке функция различает:

- падение страницы (`Page crashed`);
- остальные ошибки, например таймауты.

Для каждого типа ошибки ведётся отдельный счётчик. После достижения лимита функция:

1. сохраняет состояние через `_save_state_to_json()`;
2. выбрасывает `PageRestartRequired`.

Между попытками выполняется задержка в 3 секунды.

### 6.2. `_extract_all_match_data(page, match_ids)`

Извлекает данные всех переданных матчей одним вызовом JavaScript в браузере.

Перед извлечением функция ждёт таблицу `table#table_live`. Если таблица не появилась за 2 секунды, выбрасывается `TableNotReadyError`.

Для каждого ID функция ищет:

- время матча (`td#time_<match_id>`);
- строку матча (`tr`);
- AH-коэффициенты из `p.odds1`;
- total/over-значения из `p.odds3`;
- команды;
- счёт;
- лигу.

Результат имеет вид словаря:

```python
{
    "match_id": {
        "time": "...",
        "ah": {...},
        "ov": {...},
        "team1": "...",
        "team2": "...",
        "score": "...",
        "league": "..."
    }
}
```

Главная оптимизация функции состоит в том, что данные всех матчей извлекаются одним browser-side вызовом, а не отдельным вызовом для каждого матча.

### 6.3. `_collect_match_ids(page)`

Собирает ID видимых матчей прямо из DOM страницы.

Алгоритм:

1. находит элементы с ID, начинающимся с `time_`;
2. исключает скрытые элементы;
3. находит строку соответствующего матча;
4. проверяет наличие odds;
5. добавляет ID подходящего матча в список.

Эта функция используется после forced reload, когда состав матчей на странице мог измениться.

## 7. Класс `MatchMonitor`

`MatchMonitor` хранит всё изменяемое состояние, которое раньше находилось в локальных переменных большой функции `parse_and_monitor_match`.

### Состояние объекта

- `page` — объект страницы Playwright;
- `match_ids` — ID матчей для первоначального запуска;
- `saved_state` — состояние, восстановленное из JSON;
- `last_data` — последние сохранённые AH и OV для каждого матча;
- `active_match_ids` — текущий список матчей на странице;
- `consecutive_table_errors` — количество последовательных ошибок готовности таблицы;
- `reload_counter` — количество итераций до периодического reload;
- `reload_threshold` — случайный порог от 420 до 480 секундных итераций;
- `restart_deadline` — момент планового перезапуска.

### 7.1. `run()`

Публичный метод объекта.

Он:

1. записывает в лог начало мониторинга;
2. вызывает `_init_or_restore_state()`;
3. запускает бесконечный `_monitor_loop()`;
4. пропускает `PageRestartRequired` наружу;
5. логирует остальные ошибки, сохраняя поведение исходной функции.

### 7.2. `_handle_table_not_ready()`

Обрабатывает ситуацию, когда таблица не готова.

- увеличивает `consecutive_table_errors`;
- после трёх ошибок сохраняет состояние;
- перезагружает страницу;
- собирает актуальные ID и синхронизирует новые и исчезнувшие матчи;
- обнуляет счётчик ошибок;
- возвращает `True`, если reload выполнен.

При меньшем количестве ошибок возвращает `False`, а вызывающий метод делает паузу и повторяет попытку.

### 7.3. `_init_or_restore_state()`

Выбирает один из двух сценариев старта.

#### Восстановление

Если передан `saved_state`:

- восстанавливаются `active_match_ids`;
- `self.match_history` заполняется сохранённой историей;
- восстанавливается `last_data`.

После восстановления начальные данные заново не создаются.

#### Новый запуск

Если сохранённого состояния нет:

- `active_match_ids` создаётся из `match_ids`;
- вызывается `_load_initial_data()`;
- сразу после инициализации вызывается `find_pattern_matches(self.match_history)`.

### 7.4. `_load_initial_data()`

Загружает первоначальные данные всех активных матчей.

Функция повторяет попытку до тех пор, пока таблица не станет доступной. После трёх ошибок `_handle_table_not_ready()` перезагружает страницу и запускает полноценную синхронизацию матчей.

Важно: после reload новые ID матчей получают первоначальные записи в `self.match_history` и `last_data` только после успешного извлечения данных. Исчезнувшие ID удаляются из `self.active_match_ids`, `self.match_history` и `last_data`.

### 7.5. `_monitor_loop()`

Основной бесконечный цикл мониторинга.

Каждая итерация:

1. ждёт 1 секунду;
2. увеличивает счётчики;
3. каждые 100 итераций пишет heartbeat в лог;
4. проверяет плановый срок перезапуска;
5. при достижении `reload_threshold` выполняет `_do_periodic_reload()`;
6. получает свежие данные через `_poll_and_update()`;
7. при изменениях вызывает `find_pattern_matches(self.match_history)`.

Проверка паттернов выполняется только когда история действительно изменилась либо после добавления новых матчей.

### 7.6. `_trigger_scheduled_restart()`

Сохраняет состояние и выбрасывает `PageRestartRequired`.

Сохранение выполняется даже если оно завершилось ошибкой: перезапуск всё равно продолжается, чтобы внешний цикл `main.py` мог создать новый браузер.

### 7.7. `_do_periodic_reload()`

Периодически перезагружает страницу, чтобы обновить состав матчей и восстановить стабильное состояние DOM.

После reload функция:

- собирает новый список матчей;
- определяет новые и исчезнувшие ID;
- удаляет историю исчезнувших матчей из оперативного состояния;
- получает начальные данные новых матчей;
- добавляет новые матчи в `self.match_history` и `last_data`;
- сохраняет только успешно инициализированные ID в `self.active_match_ids`.

Та же синхронизация вызывается после аварийного reload из `_handle_table_not_ready()`. Поэтому оба типа перезагрузки одинаково обрабатывают добавление и удаление матчей.

Важно: удалиться может только ID, который уже находился в предыдущем `self.active_match_ids`. Если в логе указан матч, которого не было в первоначальном списке, он, вероятно, был добавлен при одном из предыдущих reload или восстановлен из `match_state.json`. Также список может временно стать неполным во время обновления odds, если страница ещё не закончила отрисовку.

Возвращает `True`, если список активных матчей изменился. Иначе возвращает `False`.

### 7.8. `_synchronize_matches(current_match_ids)`

Синхронизирует список матчей после полной загрузки таблицы.

Функция:

1. удаляет дубликаты ID;
2. сравнивает текущий список с `self.active_match_ids`;
3. удаляет исчезнувшие матчи из оперативной истории;
4. загружает начальные данные новых матчей;
5. добавляет в активный список только матчи, данные которых удалось получить.

Эта функция не удаляет записи из `matches.json`. Она изменяет только оперативные структуры мониторинга. Уже отправленные прогнозы остаются в постоянном хранилище.

### 7.8. `_poll_and_update()`

Получает текущие данные всех активных матчей одним вызовом `_extract_all_match_data()` и сравнивает AH/OV с `last_data`.

Если значение изменилось:

1. текущая запись добавляется в `self.match_history[match_id]['changes']`;
2. `last_data` обновляется;
3. возвращаемый флаг `data_changed` становится `True`;
4. событие записывается в лог.

Возвращает пару:

```python
(data_changed, should_continue_outer_loop)
```

При ошибке готовности таблицы возвращается `(False, True)`, чтобы внешний цикл начал следующую итерацию без дальнейшей обработки текущего цикла.

## 8. Публичная функция `parse_and_monitor_match`

```python
def parse_and_monitor_match(page, match_ids=None, saved_state=None):
```

Это обратимо совместимая точка входа для [main.py](../main.py).

Функция сама не содержит алгоритма мониторинга. Она создаёт `MatchMonitor` и вызывает `run()`:

```python
MatchMonitor(
    page,
    match_ids=match_ids,
    saved_state=saved_state,
).run()
```

Благодаря этому вызовы в `main.py` остаются прежними:

```python
parse_and_monitor_match(page, saved_state=saved_state)
parse_and_monitor_match(page, matches)
```

## 9. Как parser.py взаимодействует с logics.py

После первоначальной загрузки и после каждого изменения данных `parser.py` вызывает:

```python
find_pattern_matches(self.match_history)
```

`logics.py` затем:

1. проходит по всем матчам в переданном `self.match_history`;
2. объединяет `initial` и `changes` в историю событий;
3. проверяет over-паттерн;
4. проверяет AH-паттерн;
5. при совпадении вызывает Telegram-уведомление;
6. возвращает список ID с найденными паттернами.

`parser.py` не использует возвращаемый список, потому что его задача — продолжать сбор данных, а не принимать решение по сигналу.

Локальный импорт `find_pattern_matches` также откладывает загрузку `logics.py` до момента фактической проверки истории.

## 10. Взаимодействие с main.py при перезапуске

`main.py` передаёт страницу в `parser.py`, но сам управляет жизненным циклом браузера.

Когда `parser.py` выбрасывает `PageRestartRequired`, `main.py`:

1. перехватывает исключение;
2. закрывает текущий браузер;
3. запускает текущий Python-процесс заново через `os.execv`;
4. при новом запуске загружает состояние через `load_state_from_json()`;
5. передаёт состояние в `parse_and_monitor_match(page, saved_state=saved_state)`.

Таким образом, перезапуск браузера не должен терять уже собранную историю, если запись `match_state.json` прошла успешно.

## 11. Условия корректной работы

Для работы `parser.py` необходимы:

- объект Playwright `page` с доступом к сайту;
- таблица `table#table_live`;
- ожидаемые DOM-селекторы `time_*`, `oddstd`, `odds1`, `odds3` и другие селекторы внутри строки матча;
- права на чтение, запись и удаление `match_state.json`;
- корректная структура данных, которую ожидает `logics.py`.

При изменении HTML сайта в первую очередь нужно проверить `_extract_all_match_data()` и `_collect_match_ids()`, так как именно они зависят от CSS-селекторов и структуры DOM.

Каждый `MatchMonitor` хранит собственный `self.match_history`, поэтому несколько независимых экземпляров мониторинга в одном процессе не смешивают свои истории. При сохранении состояния в `match_state.json` записывается история конкретного экземпляра.

## 12. Краткое резюме

`parser.py` — это рабочий слой между браузером и бизнес-логикой:

- [main.py](../main.py) запускает браузер и передаёт страницу;
- `parser.py` извлекает и отслеживает данные матчей;
- [logics.py](../logics.py) анализирует накопленную историю и отправляет уведомления;
- `parser.py` сохраняет состояние и организует восстановление после перезапуска.

После рефакторинга большая функция `parse_and_monitor_match` стала тонкой совместимой обёрткой, а состояние и этапы мониторинга находятся в классе `MatchMonitor`.
